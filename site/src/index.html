The alert is never where the bug is.

On-Call Graph gives an AI agent a FalkorDB graph of your services, deploys, feature flags, owners and past incidents. It follows the failure to where it starts, fixes it, checks the fix, and remembers what happened.

Five steps, each one a graph query

The service that alerts is rarely the one that is broken. A deploy only matters if it sits on the failing path, and a feature flag reaches services it was never deployed to. These are questions about how things connect, so the agent asks the graph.

1

Locate where the failure starts

Walk downstream from the alerting service. Every possible cause is in that set and nothing else is. The deepest unhealthy service whose own dependencies are healthy is where the failure starts; everything above it is passing the error along. Changes outside the set are ruled out by name.

rank_suspectsalgo.betweennessalgo.SPpaths
MATCH p = (s:Service {name: $alerting})-[:CALLS*0..6]->(d:Service)
RETURN d.name, min(length(p)) AS hops

// a flag reaches a service it was never deployed to
MATCH (x:FlagChange)-[:TOGGLED]->(:Flag)-[:AFFECTS]->(d:Service)
WHERE d.name IN $candidates AND x.at >= $since
RETURN d.name, x
2

Confirm with logs and memory

Read the logs of the top suspect only. Search incident memory with a full-text index plus graph overlap, and pull the root cause and the fix of anything similar. A runbook attached to the service travels with the answer.

get_logsfind_similar_incidentsget_owner
CALL db.idx.fulltext.queryNodes('Incident', 'checkout|timeout|fraud')
YIELD node, score
MATCH (i:Incident) WHERE i.id IN $ids
OPTIONAL MATCH (i)-[:ROOT_CAUSE]->(rc)
OPTIONAL MATCH (i)-[:RESOLVED_BY]->(a:Action)
RETURN i, collect(rc), collect(a)
3

Act, dry run first

Roll back, restart or flip a flag. Each action defaults to a dry run that shows the plan and its blast radius. A Claude Code hook refuses any real action without a matching dry run in the graph from the last 15 minutes, so the safety policy is itself a query.

// PreToolUse guard: no blind remediation
MATCH (a:Action {kind: $kind, target: $target, dry_run: true})
WHERE a.at >= $fifteen_minutes_ago
RETURN count(a)

// every action is explainable later
(:Action)-[:BECAUSE]->(:Evidence)   (:Action)-[:REVERTS]->(:Change)
4

Verify on the service users hit

Poll the alerting service until it is healthy twice in a row. If it is not, rank again from the new state. The agent is allowed at most three actions.

5

Page the owner and remember

Find who is on call through the ownership graph and page them with the evidence path. Resolve the incident with a ROOT_CAUSE edge to the exact change. The next agent, in a different session, finds it.

RETURN t.name, p.handle, e.name, ep.handle

Does the graph matter?

Same model, same actions, with and without the graph

Each failure is injected into the live stack and the same headless agent runs twice: once with the FalkorDB tools, once with only health, logs and a flat change list. We ran it with full telemetry, where stats say where errors originate the way tracing does, and with basic telemetry that has error rates and latency only.

The graph

      
Everything the agent knows is a node or an edge

      


// topology and ownership
(:Team)-[:OWNS]->(:Service)-[:CALLS {declared, observed}]->(:Service)
(:Person)-[:ON_CALL_FOR]->(:Team)-[:ESCALATES_TO]->(:Team)
(:Runbook)-[:FOR]->(:Service)   (:Flag)-[:AFFECTS]->(:Service)

// what changed
(:Change:Deploy {version, prev_version, at})-[:CHANGED]->(:Service)
(:Change:FlagChange {flag, from, to, at})-[:TOGGLED]->(:Flag)
(:Person)-[:AUTHORED]->(:Change)   (:Deploy)-[:ROLLED_BACK]->(:Deploy)

// incident memory and provenance
(:Incident)-[:IMPACTED]->(:Service)
(:Incident)-[:ROOT_CAUSE]->(:Change | :Service)
(:Incident)-[:RESOLVED_BY]->(:Action)-[:BECAUSE]->(:Evidence)
(:Action)-[:REVERTS]->(:Change)
(:Investigation)-[:STEP {n, tool, at}]->(any node the agent looked at)

        
    
          
  • Built from real sources. Services, owners and declared calls come from Docker Compose labels; observed calls and live health from each service's stats; deploys and flag flips from the change log; runbooks from Markdown front-matter.
    • 
          
  • Read-only reasoning. Every query the agent's tools run goes through GRAPH.RO_QUERY with a 2 second timeout and a row cap. Only deterministic code writes.
    • 
          
  • Idempotent ingest. Every sync is a MERGE on a stable key, so the graph can be rebuilt from its sources at any time.
    • 
          
  • Algorithms as tools. algo.betweenness breaks ties between suspects; algo.SPpaths returns the evidence path the agent shows you.
    • 
          
  • Investigations are data. Each tool call is a STEP edge to the nodes it looked at. The dashboard and this page replay them.

On-Call Graph was built for Graph Hacks: Context for AI Agents (WeMakeDevs × FalkorDB, October 2026). Apache-2.0.

      
Prior art: woodpecker-mcp also keeps a service graph in FalkorDB, with analysis only. AWS DevOps Agent, Datadog Bits AI SRE, Dynatrace and Causely use topology graphs inside their own platforms. On-Call Graph is open, self-hosted, acts and verifies, remembers, and runs inside the agent you already use.

    

    

      
Built with Claude Code as a pair programmer. At runtime the agent is Claude, through Claude Code headless or any MCP host. No model training anywhere.

      
The replays on this page are recordings of real runs against the demo stack, played back in your browser.
